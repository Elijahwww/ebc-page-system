# EBC 跨 AI / Agent 交接协议 v0.1

> 状态：USER_WORKFLOW_DERIVED / RUNTIME_NOT_YET_VALIDATED。适用 GPT、Claude Desktop（含 Code）、Gemini、Grok、Cursor 等。**不假设不同 AI 能直接互相发消息、自动同步聊天记忆或自动获得同一 GitHub 权限。**
> 目标：切换模型后**不丢用户原始需求、不覆盖已确认中文文案、不重复调研、不把候选方案误升为最终方案**。此协议负责交接，不替代 PM 五节点深度审查或独立翻译流程。

## 一、只有一份项目事实来源（Single Source of Truth）

每个真实项目以 `projects/<slug>/` 为唯一项目工作区；跨模型均从同一个 `brief.md` 与当前已确认文件版本读取，而不是以各自聊天的最新消息为唯一事实。

| 文件 | 职责与权威性 |
|---|---|
| `brief.md` | 保留用户需求原文、目标市场/语言、时间、任务目标和更改记录；只有用户新指示可以覆盖原目标 |
| `pm-decision.md` | 当前推荐的需求解释、研究、用户路径、方案取舍及关键假设；可由 PM 主控更新，变更要追踪 |
| `copy-sheet.md` | 中文源文案的唯一现行版本；逐条 Copy ID、状态、版本和上下文；确认文本受保护 |
| `design-spec.md` | 当前设计/交互说明；必须引用对应 PM 决策和 Copy Sheet 版本 |
| `demo/` | 当前可运行实现与测试状态；不得被当作当前业务事实来源 |
| `runs/<agent>-<date>/` | 各 Agent 的独立候选、研究或 QA 结果；不自动覆写项目主文档 |
| `iterations.md` | 由谁在什么版本改了什么、为什么、是否获用户批准及怎样验证 |
| `handoff.md` | **当前交给下一个 Agent 的最小可执行上下文**，不是重复所有对话全文 |

适用优先级：**用户最新明确决定/当前真实业务事实 → 项目被确认的简报与中文文案版本 → 经过核验的来源 → PM 当前推荐策略 → 历史源码/外部参考 → 各 AI 草案**。发现冲突不得自己合成虚假的“已确认版本”，须记录 `CONFLICT` 并回报真正需要解决的问题。

## 二、什么时候交接？
- PM 研究 / 用户心理 / 文案 / 方案相互挑战时，可随时委托另一个 AI 独立处理特定问题，不必等线性节点“完成”。
- 中文文案/方案确认后，可交给 Claude 等实现；确认之前也允许做 **明确标记的探索 Demo**，不得把探索稿写为获批终稿。
- 开发发现 CTA、页面结构或文案逻辑不成立，应把具体问题返回 PM/Copy；不自行改写已确认语义。
- Gemini/Grok 的研究和审稿属于**建议与证据来源**，不是自动批准，也不是最终真实用户数据。
- 语言本地化只有在中文源文案确认后启动；目标市场特别要求（如 Japan 活动）在 PM 研究阶段先考虑，参见 `localization/chinese-first-and-market-overrides.md`。

## 三、交接包（Handoff Packet）最少 9 个字段
统一写入 `projects/<slug>/handoff.md`，可使用 [模板](../projects/HANDOFF-TEMPLATE.md)。原则：一屏内能知道“接下来做什么”，具体证据通过文件路径追溯。
1. **项目识别**：项目 slug、目标市场、工作语言 `zh-CN`、当前任务类型。
2. **版本锚点**：Git 分支 + commit SHA（或明确本地尚未提交），上一次交付时间与依赖文件版本。
3. **上游决策**：当前已确认事实、目标、PM 结论；**哪些只是建议/未知**。
4. **中文文案锁定状态**：Copy Sheet 的具体版本，逐条确认/待确认 ID；有锁定文案就严格引用，不重写。
5. **下一 Agent 的清晰任务**：要回答的决策问题或交付的文件，而不是泛泛“继续优化页面”。
6. **允许修改的范围**：哪些可以改、哪些禁止改；如产生冲突应提交什么问题。
7. **必读资源**：本项目的 2–5 个关键路径、外部来源链接与查看日期，避免一次性重新加载全仓。
8. **验收标准**：能够观察、复核的具体结果，如 V1→V2 修改、截图真伪、Demo 实际运行/移动 QA。
9. **输出位置及回流对象**：独立 `runs/` 文件夹、建议合并进哪些主稿、需要人工选择的分叉。

仅改一段 Banner 的 QUICK 任务可简写，但**原句、状态、上下文、目标、变更边界**必须保留。

## 四、接收 Agent 的首要动作（READ → VERIFY → WORK）
1. **READ**：读取 `AGENTS.md`、项目 `handoff.md`、列出的具体版本文件；检查 Git commit/分支是否与交接包一致。没有仓库权限时，请求提供最小交接包或相应文件，不要声称“已经读取 GitHub”。
2. **VERIFY**：复述自己负责的问题、已锁定内容、允许调整范围；检查版本/引用和数据状态。上游链接失效或版本落后则停止覆写，记录 `STALE_HANDOFF` 并请求更新版本/检查最新仓库。
3. **WORK**：按本节点 Skill 独立研究、反证、实质改进；需要调用其他 AI 的成果时通过仓库文件或简要交接包读取，不假设访问对方私有对话。
4. **RETURN**：写候选结果到自己的 `runs/<agent>-<date>/` 或约定工作文件，附：发现、具体修改、依据、未决项、下游需要做什么。获得实际权限并有人类明确确认后才更新锁定主稿。
5. **LOG**：重要变更记录到 `iterations.md`。可推广的方法问题再提议修改全局 Skill/规则；单个项目意见不自动升级全局规范。

## 五、需要保护的四种内容
- `USER_APPROVED_COPY`：用户明确确认的当前中文句子与 Copy ID/版本；**另一个模型的建议不可直接覆写**。
- `APPROVED_PROJECT_DECISION`：用户已确认的页面目标、受众、行动或结构；若新证据冲突，提出变更理由让用户选择。
- `EVIDENCE`：实际来源、时间、适用市场、真实截图/HTML 状态，不能被演绎为真用户数据或 CTR/CVR。
- `WORKING_CANDIDATE`：研究初稿、其他 AI 的反例、概念稿、演示占位；不得继承“已批准”标签。

当两个模型给出相反建议时，PM 主控应对照**用户问题 → 证据 → 目标市场 → 用户路径 → 变更成本**作对抗比较，把未胜出的建议也记录在 `runs/` 和 `iterations.md`；**人工决定价值冲突，不要求用户处理技术细节**。

## 六、跨客户端的现实边界
- **GitHub 已连接且有权限**：读取同一项目文件；写入应遵守当前仓库权限与版本管理方式。
- **Claude Desktop 本地 Code**：可打开本地 GitHub Desktop 已克隆的目录；本地修改要通过 GitHub Desktop/ Git push 同步，其他 Agent 不会立刻看见未推送内容。
- **Gemini/Grok 仅能导入快照/粘贴材料时**：交接包必须有 Commit SHA 和更新时间；过期快照不应被误当最新 `copy-sheet.md`。
- **仅对话、没有仓库权限**：粘贴 `handoff.md` 核心内容与必要的批准文案/截图或文件片段；不要上传整个私有仓库、Token 或客户资料。
- **不同 AI 之间没有天然的自动任务调度**：用户/协调 Agent 通过文件/连接器传递结果，不能声称已经自动通知另一个平台。

## 七、反模式与最小成功标准
FAIL：
- 下游重新写一份与确认版冲突的文案并称“优化完成”；
- 用另一个 Agent 的临时讨论结论覆盖 `brief.md`；
- 引用未同步的本地文件却称全员可读；
- 把不同市场、不同版本的页面资料混成一个当前定稿；
- 只写“已交给 Claude”但没有真实共享文件/可读取的路径；
- Agent 评审没有留下具体要修的项目与来源，只有“更专业/更有设计感”。

PASS：换模型后无需重讲背景，能定位当前**唯一**目标、确认文本和版本，执行独立任务，留下可复查的结果与后续动作；没有真实跨平台连接时如实说明交接方式。
