# EBC Agent System · 迭代记录与持续优化

> 从 2026-11-12 起，本仓库采用 **main = 最新可用系统基线** 的工作方式。所有真实页面项目都属于正常生产流程，而不把“测试”当成独立的一套临时规则。此处记录方法/Skills/规则的迭代，真实页面项目的产出另存 `projects/`。

## 运行模型
1. 从 `main` 获取最新的 PM / Research / Copy / Design / Dev 约束。
2. 处理真实项目：需求 → 五节点互相回退的 PM 循环 → 完整文案与结构 → 需要时设计和可运行 Demo → QA。
3. Agent 的结论、项目素材与产出放在 `projects/<project-slug>/`；不要覆盖 `sources/` 的历史原件。
4. 收到用户批注、真实数据或发现新参考后，更新该项目的决策与修订记录，再判断是否是**全局可复用**的知识。
5. 新知识/规则/Skill 改进尽量在小分支完成并合并 PR 到 `main`；对少量明确的日志/项目文档也可以按团队习惯直接提交 `main`，但不要静默覆盖重要全局规则。
6. 每次迭代都记录：当前问题、证据、变更前/后、修改原因、受影响文件、如何验证、下一次何时重查；无证据的经验只能标 `RULE_CANDIDATE`。
7. 重大失误可回退 Git commit/PR；不得直接修改或删除过去的迭代记录。

## 文件区分
- `CHANGELOG.md`：版本里程碑与已合并变更的摘要，便于 Agent 快速识别新旧。
- `iterations/YYYY-MM-DD-<topic>.md`：一次真实机制调整的完整决策记录。
- `projects/<slug>/iterations.md`：同一个页面/项目的 V1→V2→V3 内容和页面变化。
- `projects/<slug>/evidence/`：来源/截图定位与版本，不把第三方无授权原素材当 EBC 生产资产。
- `pilot/`：保留初始多模型比较评估标准，但**不再是默认只允许测试的执行模式**。

## 每条机制迭代至少回答
| 字段 | 内容 |
|---|---|
| Trigger | 哪个真实项目问题或 Agent 错误触发？ |
| Scope | 影响 PM / Research / User / Copy / Strategy / Design / Dev 哪些节点？ |
| Evidence | 具体 URL、项目文件、截图、用户审核意见或真实数据 |
| V1 → V2 | 被实质修改的句子、判断、模块、规则或代码 |
| Why | 为什么修，最大的反对证据是什么？ |
| Status | HYPOTHESIS / RULE_CANDIDATE / USER_CONFIRMED / APPROVED_RULE |
| Validation | 哪个案例或真实 Agent 回归测试能够复现改善？结果是什么？ |
| Compatibility | 哪些旧项目/语种/市场不适用？ |
| PR / Commit | 变更来源，供回滚和审查 |

## 原则
“新案例出现”不意味着立即推翻全局标准；一条真实反馈可以先更新项目级例外。只有跨案例重复成立或用户明确作为可推广规范认可时，才提升为公共模式。
外部调研页面和截图必须注明实际取得的证据类型；没有真实截图，不能称做过视觉验证。
