## 一、哪些结论可以作为目前的默认候选？

| 页面类型 | 来源直接支持的稳定观察 | 建议候选结构 | 不可硬化的部分 |
|---|---|---|---|
| 交易激励活动 `CAMPAIGN_TRADING_INCENTIVE` | 3/3 独立代码含页面导航、Hero 内嵌注册、奖品、参与步骤和规则；2/3 在奖品之后另有机制/榜单；第三例是排名型，第一例升级奖券，第二例门槛归奖品 | `Hero+Form → Prize → (Mechanism/Leaderboard if needed) → Steps → Rules`；系统导航及适用的风险/版权内容按生产要求另核 | 并非“三类交易大赛”；只有 1 例排名、1 例达标、1 例抽奖；“三步”是观察不应对新复杂报名流程强制三步；表单必须嵌入仅属历史默认 Variant |
| 产品获客 LP `LP_PRODUCT` | 3 个**产品家族**共 7 个 Vue 版本均有 Hero、`section2~4` 三个主内容位，以及 CTA→注册弹窗；ETF/OIL/CT 的尾部/步骤由不同代码或共享组件决定 | `Hero → Trust/Regulatory when applicable → 3 role-based content slots → Closing cluster → CTA/Legal` 作为**可调整的初始模板** | “恰好 3 个正文模块最优/禁止第 4 个”没有转化或理解实证；不应因某槽位空缺就无关补齐。Hero 精确两行是已有写法，不是强制 |

### 交易激励活动的三种机制（不是三种生命周期）
- `CMP-TC-01`：双十一，抽奖券随净入金获取、交易手数升级；代码直接有独立 `section3`。
- `CMP-TC-02`：Trade Up，达标领取，页面只有 `section2` 奖品、`section3` 步骤、`section4` 规则，`page-cta` 收尾；**没有独立排行榜/机制**，资格写奖品卡的视觉来源仍需线上审视。
- `CMP-TC-03`：泰语代码有 `rankingTable eventId=…`，活动规则与视觉大量以背景图导入；**PC 设计、移动设计、代码和 URL 不是同一场赛事**，不应将它们视为相互核对的一个线上版本。此目录中的“相同模块”说明历史实践存在结构复用，不能证明这些文件彼此对应。

## 三、正确的应用方式：Baseline-first, not Template-first

1. **先用户目标**：受众、入口（广告/站内/SEO）、业务机制、核心行动、产品/活动事实和必要披露，决定需要回答的用户问题。
2. **再候选结构**：按 `README.md` 识别 `Page Type`，找最近似且**适用**的案例骨架，确认是用户锁定、跨版本观察还是单例。
3. **先同模块变体**：针对不同主题替换文案、视觉、奖品、真实交易数据，优先合并/折叠/下沉内容。
4. **新增准入**：仅当现有模块无法承接真实信息/行动或必要披露，提出 `Structure Override`，写新用户问题、为何无法放旧模块、放弃/代价、证据及纠错信号。
5. **可以做减法**：候选结构不是“必须填满所有历史槽位”；每一项真正的 Required 只能根据用户批准的结构或不可省略的业务/法律事实成立，不单靠历史出现频率。
6. **方案竞争讲取舍**：已有结构时对比同骨架下的证据/信息深度/CTA/Variant/用户路径，而非必须新增页面区块；未有适用结构时才比较明显不同的模块叙事或选择不做页。
7. **视觉自由**：固定职责不等于固定卡片形状、字号、深色 Hero 或动效；视觉迭代单独按 `design/methods/visual-direction-and-iteration.md`。
8. **用户确认状态**：此轮研究只是 `GPT_REVIEWED_CANDIDATE`，无 `STRUCTURE_LOCKED`。需要用户明确确认骨架适用范围后才更新状态。不能用 ChatGPT 自己的“建议采用”替代用户批准。

## 四、待业务核对，而非由 GPT 代替作决定

| 优先级 | 问题 | 当前可做动作 |
|---|---|---|
| P0 内容事实 | ETF 活动是否续期/收费与股权表述是否合法准确、某些过期文案是否仍被投放 | 标为历史内容高风险，不用它生产新页面；业务审批后取批准版 |
| P0 市场与实体 | 各活动实际是否出现完整风险披露/版权；是否有单独法律实体显示 | 线上可用环境复核 + 合规确认；不把代码缺失等同线上缺失 |
| P1 结构证据 | TC-03 多场赛事文件混放；TC-02 奖品/规则图片化；移动榜单行为无组件源码 | 保留单独来源，不合并其内容为一个获批事实 |
| P1 使用边界 | 活动 Hero 是否始终内嵌表单、LP 是否永远 3 正文位、官网 FAQ 是否必备 | 按真实需求+候选骨架做决策，不急于锁全局 |
| P1 产品归属 | US-X 对应哪个市场/上线 URL，官网其他产品页缺真实案例 | 标待核实，未补全前不创建硬规则 |
| P2 资产治理 | 三个新增活动缺 manifest / INDEX 登记 | 本 PR 补非侵入式 manifest、来源索引；源代码和设计不动 |

## 五、取舍记录（不是“完美方案”）

**选中**：结构候选作为默认参考 + 模块证据门槛 + 必要业务/法规信息优先 + 允许例外。

**主动放弃**：立即将三个正文位/所有活动 Hero 表单/固定三步做成强制标准；以及任何「凭 AI 创意多加 FAQ、品牌故事、平台介绍」的默认行为。

**代价**：新类型/新机制遇到真实差异仍需 PM 做一次简短判断；而不是“一键套用”。这是为了避免复制错的结构、减轻未来无效页面与合规风险。

**推翻条件**：如果多项独立新案例、真实用户反馈或有可比性的转化数据显示某个结构/CTA 路径更有效，重开结构判断；用户明确批准的具体项目结构优先于候选，但新的法定披露/真实事实变化会要求复审。
