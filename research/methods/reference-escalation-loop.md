# Reference Escalation：从内部案例缺口到外部研究再回流的闭环

> 状态：SHARED_METHOD_CANDIDATE（PM / Copy / Design / Strategy / User Journey / QA 共用）
> 目的：打破“现有规则写不出来 → 继续编造 → 草草结束”，将 Agent 的问题转变为可调查的研究问题。

## 地区与搜索排序
`working_language=zh-CN` 不决定目标市场。若需求明确 Japan 等地区，**T1/T2/T3 仍按行业相关性逐层扩大，但在每层优先寻找目标地区、目标语言、目标渠道的官方页面**，并记录当地市场差异；没有对应官方资料时才扩大地区，并标注迁移风险。不要以中文写研究报告就只检索中国网站。普通全球项目不需为所有小语种提前研究、截图或做翻译。见 `localization/chinese-first-and-market-overrides.md`。

## 0. 何时启动？（不是只限于“没有案例”）
以下任一成立，主动触发且**无需用户再次许可**（在可访问工具范围内）：
- `NO_MATCH`：知识库缺同类型页面/模块/受众/地域的有效 EBC 案例。
- `LOW_CONFIDENCE`：已有案例只有历史源码或用户修改方向，缺足以支持当前选择的证据。
- `CONFLICT`：两个被引用的 EBC 案例矛盾，或者用户新要求推翻旧习惯。
- `STAGNATION`：已有 PM/C/S/U/Design 节点两轮修改仍是同义改写，没有更好的问题/反例/结构。
- `NOVEL_PROBLEM`：新产品、用户路径或形式没有成熟的可参考方案。
- `USER_REQUEST`：用户显式要求看行业/头部案例或实时网页。
- `HIGH_IMPACT`：品牌首页/核心新产品/重点转化页的重大决策，单一历史案例不足以支撑，即使“内部有类似页面”，也可做针对性外部校验。

启动前先声明 **要解决的具体决策问题**，如“招聘 Hero 表达什么职业价值，岗位搜索应何时出现”，而不是泛搜“好看的网页”。

## 1. 按行业与任务相关性逐层扩展（从高到低）
- T0 本地 EBC：已经通过用户审稿的同任务文案决策卡/页面/已确认 Brief → 识别经验是否足够。
- T1 最直接行业：Forex/CFD/在线券商/交易平台，**尽量同页面类型、同受众目的**；先搜至少 2 个具代表性的官方页面，可无匹配时如实标注。
- T2 相邻大金融/Fintech：银行、投行、资产管理、支付/金融基础设施，选择**同用户任务**而非同品牌规模。
- T3 头部科技/跨行业：Apple、Microsoft、Google、Stripe 等，拆解普适的职业叙事、产品说明、FAQ、模块、UI 交互。
- T4 有确切理由再横向寻找同页面工作最强的其他领域，包括 SaaS、消费品牌或公用事业等。

T1/T2/T3 是**搜索顺序优先级**，不是“只要行业同源就更优”的质量结论。样本选择同时兼顾：页面任务一致性（最优先）、受众/语言/市场匹配、来源可信与时效、可观察深度、独创信息价值。为跨行业引用写 **TRANSFER_RISK**（业务模式与用户动机差异）。如 T1 证据非常强可缩减 T2/T3；若任务需要故事/视觉创新而行业同质化，继续 T3 进行对照。

## 2. 执行流程：以决策为中心的动态循环
1. `GAP`：写明现有 EBC 案例为什么不足（缺招聘页同类、只有旧版、没有用户批准、视觉不符合目标等）。
2. `SEARCH_PLAN`：从 T1 开始选官方页，记录搜索词、地区语言、任务；再逐层升级。
3. `FETCH`：取真实页面和页面文本；如果能用浏览器，抓取关键截图（详见 page-capture-and-analysis.md）。网页重定向/被拦截须说明。
4. `DECOMPOSE`：对每个样本拆 Hero/副标题/证据/岗位搜索/CTA/人群入口、模块顺序、信息作用、互动及移动变化。分别标直接观察 vs 分析推断。
5. `CROSS_COMPARE`：比较 **相同用户问题** 的不同答案，而不是比较哪家口号更“高级”。
6. `CHALLENGE`：至少找一例与主流模式不同、可能证明原假设不成立的反例。
7. `TRANSFER`：明确哪个**机制**可迁移，哪些具体句子、数据、图片、权益/功能不能迁移；禁止因为“Apple 这么写”而覆盖 EBC 已确认文案。
8. `USER_REPLAY`：回 U 节点，用目标受众至少 2 种路径复核期望、误解和行动阻碍（模拟=假设）；再由 C/S/Design 形成差异明显的 V1→V2。
9. `VERIFY`：修改后的文案/结构/视觉是否真的解决了最初的空缺？若没进步或发现新矛盾，按节点循环再搜，必要时 T4。
10. `ARCHIVE`：有新发现才产生 evidence card / candidate pattern，带 URL/日期/截图状态/适用条件/反例/结果。不得未经验证提升为 EBC 正式规则。

## 3. 每轮资源投入上限与升级条件
- QUICK：优先内部；外部 1–2 个高相关的官方页面/关键区块，研究不应比小文案修订更耗时。
- STANDARD：T1 通常 2–3 页，问题未解决则 T2 1–2、T3 1–2；取样建议，不是凑数 KPI。
- DEEP：大改版可扩大样本、地区/语言与移动/PC 维度、对抗性研究；但仍以“研究有没有改变结论”为停止条件。
- 发现清楚、可迁移、可反驳并已修订方案，则停止抓取；如果只得到概念相似的文案而没有决策增量，扩大范围或调整研究问题。
- 没有可截图工具时，**不要把“文本检索”当完成视觉分析**；允许给出带局限的暂定文案/策略，视觉环节标 PENDING。

## 4. 节点间调用规则
| 触发节点 | 要找的外部证据 | 必须回流 |
|---|---|---|
| D / 需求 | 同类产品/页面到底解决什么问题、有没有非页面替代方案 | 回 D 重构需求与问题假设 |
| R / 调研 | 行业、相邻行业、跨行业页面反证、竞争机制 | 回 R 的来源矩阵与策略结论 |
| U / 用户 | 页面实际解释/信任/表单/步骤与认知差距 | 回 U 假设路径，给验证计划 |
| C / 文案 | H1、subtitle、模块职责、CTA 与功能/场景关系 | 回 C 产生具体改写和重新走读 |
| S / 方案 | 模块顺序、谁先解释/谁先证明/是否分流 | 回 S 竞争多种信息架构 |
| Design / UI | 实际模块布局、视觉层级、留白、图片角色、移动断点 | 回 Design 的 override、草图/交互变更 |
| QA | 竞品/对照案例可帮助识别遗漏，但仍以需求与真实规范验收 | 回对应 D/C/S/Design 修正，禁止“别人这么做”强制修改 |

## 5. 来源和质量记录（必须保留）
每个页面至少：真实 URL、来源层级、公司/页面类型、采集日期和地区语言、访问状态（HTML/截图）、PC/MB 视口信息、最相关的 2–5 个模块任务、原文有限摘录或语义概述、交互观察、分析推断、对 EBC 可迁移点与不可迁移点、具体反证、关联原决策及版本差异。
不同时间抓取的同一 URL 不互相覆盖；后续巡检如实际发现变化，创建新版本。

## 6. 反模式
- 一次性抓大量竞品，最后只输出“简洁、专业、国际化”。
- 不经用户路径验证就照抄 Apple/Goldman 的职业福利或文案。
- 只看截图却不知道实际 HTML 文案和 CTA 点击到哪里。
- 只看 DOM 文案就声称分析了图片、排版、首屏/滚动节奏。
- 复制外部 Logo/素材/网页源代码给 EBC 使用。
- 没有来源、时间/地区、证据强度，就提升到 APPROVED_RULE。
- 因为担心找不到答案便向用户索要所有竞品 URL；应先由 Agent 自主研究。
