# 从需求到文案定稿：带证据的循环编辑协议 v0.1

> 状态：METHOD_CANDIDATE，与 PM `D/R/U/C/S` 中的 Copy 节点配合。目的不是让模型模仿一些漂亮例句，而是还原用户曾经反复斟酌的具体判断。

## 默认生产顺序
- 先以中文进行完整 PM/Copy 分析、备选文案的审查循环及中文 Copy Sheet 确认，然后把 Copy ID、事实限制、语义和用户任务作为本地化输入；此阶段不要提前并行翻译所有语言。
- 中文是内部主稿语言，**不等于该文案给中国市场用户看**；日本等地区定向文案应在创作中文主稿之前研究目标市场的用户意图及当地行业表达。
- 翻译阶段做本地化创作，不逐字直译；改变信息职责或事实时回流中文主稿审查。详见 `localization/chinese-first-and-market-overrides.md`。

## 0. 输入（尽量由 Agent 自行读取）
- 页面类型、用户/市场/渠道、一次想解决的认知问题；
- 当前产品状态、需要写入的真实事实、可能的市场限界；
- 已确认的模块结构/CTA 行为、现有已批准 Copy Sheet（若有）；
- 同类 EBC Copy Decision Cards + 历史在线/源码样本（**状态明确**）；
- 原始用户的修改意见和拒绝原因。

## 1. 先提出任务，不先“写十个标题”
把每个关键模块转成：
- Before：用户进入模块前已经知道/相信什么；
- Gap：现在缺哪一个必要认知？
- After：读完之后应该明确什么？必须是正确理解；
- Evidence：用哪个产品行为/事实/来源支撑？
- Action：下一步在哪里，用户需要做什么？

如果这个模型填不出来，返回 PM 用户路径/研究，不靠文案辞藻掩盖事实不足。

## 2. 参考检索要具体到“类似的用户任务”，不是同样的产品关键词
- EBC-COPY-004 职业价值，不适用于 ETF 产品介绍；但“能力认可→行动可能”的结构可作为如何拆双信息的教学例。
- EBC-COPY-002 监管副标题的“主体/适用范围补全”，可应用于其他需要说明范围的信任模块，但不能照搬监管夸赞词。
- Oil B 的具体交易机制比 Oil A 的生活场景适合有原油交易认知的人；若目标是普通 SEO 产品介绍，可能需要两种解释结合。
- 需要避免同一个历史 LP 的文案模式压制品牌官网的不同信息职责。

## 2A. 现有标准无法回答时的外部研究回路
在 EBC 已确认文案不足、被历史样本限制、文案几次修改仍是同义词、或页面类型完全新时，触发跨节点 `research/methods/reference-escalation-loop.md`，当前位于 `main` 的 `research/` 目录。按 CFD 同类型页面 → 大金融/金融科技 → Apple 等全球科技头部的同一**页面任务**比较 H1、subtitle、模块职责、信息分布与 CTA。真实截图与页面 DOM 共同理解页面；缺截图标 `TEXT_ONLY_VISUAL_PENDING` 不臆测排版。拆解“为什么可能这样写”，再结合 EBC 用户心理和业务事实形成原文 V1→候选 V2，不抄字句/未授权素材。外部网页的原理只是 BENCHMARK_CANDIDATE，无法自动变成 USER_CONFIRMED 或 APPROVED_PATTERN。

## 3. V1：不同策略的文案候选
至少两个真正不同的切入：
1. **直接信息型**：是什么/能做什么/下一步；
2. **用户阻碍型**：当前替代方案困难是什么/本产品如何帮助理解或执行；
3. **具体机制与证明型**：真实参数、操作、条件或品牌事实；
对于状态页，可用“状态事实型”；对于品牌页可用“事实关系型”。
每个候选包含 H1+subtitle+必要前后文，不能只发一句孤立标题。

## 4. V1 审稿必须用已确认案例反证
使用 review-rubric 的 4 个否决项 + 8 维 0–2 评分，并填原因。
强制回答：
- 哪句与已确认标准冲突？对应 EBC-COPY ID 是什么？
- 哪个词或主张容易误解？**具体解释可能怎样误解，而不是只说“有歧义”**。
- H1 与 subtitle 是否重复？去掉其中一句会损失哪条信息？
- 对于不同流量入口、不同知识程度，何处仍无法继续？
- 是否把旧源码上线文案误当最终 approved？
- 是否在内容中无意义叠加“全球/顶级/专业/一站式/机遇”等营销词？
- 若删除装饰性措辞，最重要的可理解信息能否保留？

## 5. V2：必须有真实编辑差异
- 实际删除/替换某句/某词，或改变模块信息职责与顺序；
- 出示改前→改后、缺陷→修复机制，证据或推断状态；
- 连读 H1+subtitle+第一模块+CTA，检查用户视角的理解梯度；
- 再走一遍 3 类用户路径（继续/犹豫/错误预期退出）；若文案不能解决，转回 U/R/S，不用继续改同义词；
- 无新证据时可暂定 V2，但须保留主张和适用范围的假设，不以“自审通过”代替用户认可。

## 6. 推荐文本与资产回写
输出一份面向生产的 `COPY_DECISION_PACKET`：
- 用户问题与场景；
- 主要/备选文案（完整上下文）；
- 与已确认 EBC 案例的对应逻辑、为什么适用/不适用；
- 最关键的拒绝原因及 V1→V2；
- H1、副标题、CTA 的信息分工；
- 文案 ID、状态、事实来源、适用语言/市场、最终点击目标；
- 已确认与待确认清单（最少必要项）。
本次审查若用户明确选择新句 → 新增 Decision Card；没有明确确认就留 CANDIDATE，不能将模型自评 PASS 改成 USER_CONFIRMED。

## 7. 输出与长度
- PM/C 交付优先给能直接读的最终候选文案及其理由，不强迫用户阅读冗长研究札记；
- 深度审查日志保留在文档中，供未来 Agent 做类似任务时检索；
- 文字长短由内容信息任务决定。UX 是否清晰不可由“20 字内/一句话”单独测定。

## 8. 版本标记
`source_version`、`author`、`reviewer`、`decision_date`、`state`、`superseded_by`、`language`、`market`、`placement`；所有原始用户否定和确认意见都应可回溯，不覆盖历史卡片。
