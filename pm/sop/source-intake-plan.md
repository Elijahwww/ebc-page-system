# PM 内部资料收集与接入计划 · v0.1

> 状态：INTAKE_PLAN；2026-11-11。仅列出下一批需要的真实资料，不代表公司既有规定。可直接上传原件，无须额外重写文档。

## 目的
将已存在的通用 PM 诊断方法转化为 EBC 实际可用的需求处理与页面方案工作流。Claude 当前负责历史 LP/官网页面案例提取，GPT 负责 `pm/` 内容与待确认规则；两者分别创建分支，绝不直接修改 main。

## P0：首先提供（有多少给多少）
1. **需求处理 SOP / 工作规范**：需求从哪里来、如何判断优先级、谁确认需求/方案、谁分配给 BA/IT/Design、哪些环节需要审批。
2. **一条已走完流程的真实项目工单**：Jira 或 PRD（可脱敏），最好附当时的需求背景、讨论/改动、方案/文案评审和最终验收。目的在于验证 SOP 如何落地，而非仅看书面规定。
3. **项目交付标准**：PM 如何定义完成，设计/开发/文案的交接方式，UAT 和上线门禁；没有独立文件可通过真实邮件/工单示例替代。

## P1：第二批补充
4. **业务事实与审批资料**：已批准的实体/地区/产品适用性、监管披露和品牌数字主张（以最新有效材料为准），并标明发布负责人。
5. **渠道与转化实务**：表单/注册跳转、Client Portal/CRM、UTM/埋点、线索质量和投放目标，允许用脱敏流程图和数据字典。
6. **跨部门协同样例**：典型的 MKT、Sales、Compliance、Design、IT 沟通与升级边界。
7. **历史需求复盘**：被拒绝的需求、方案重大修改或上线后发现问题的例子（各 1-2 条比大量普通任务更有价值）。

## P2：后续持续完善
- 目标市场/语言差异、活动专题规则、用户研究/客服反馈、竞品观察与成效分析。
- 经正式批准的品牌和文案规则、QA/SLA、开发与本地化资产可继续进入各自目录，不要求本轮全部提供。

## 每份资料建议保留的元信息（能获得就记录，未知不强求）
- 原始文件名/URL、项目或工单名称、日期/版本、提供团队/Owner
- 所属国家/语言/产品、是否仍有效、是否有替代版本
- 保密级别（仅内部 / 可入私有仓库 / 仅本地索引）
- 涉及客户个人信息、密钥或商业敏感信息的文件应先脱敏，不默认上传 GitHub

## GPT 接入后的处理步骤
1. 原文/截图/邮件为 `SOURCE`，不把推断写回原文。
2. 列出流程节点、责任人、输入材料、产物、审批门禁与异常路径。
3. 与 `pm/methods/` 现有候选规范做差异对照（MATCH / ADD / CONFLICT / OBSOLETE / UNKNOWN）。
4. 形成规范候选 + 可执行 PM Skill + PM 交接模板，标记依赖和证据。
5. 通过独立 PR 提请确认后才提升到 `APPROVED_RULE`。
6. 规则变更保留版本、适用范围、来源及回滚路径。

## 验收定义
- PM 能看懂为何推荐/反对某个页面方案，而不是只收到模板化结论。
- Agent 不会根据历史案例或公开网页编造内部流程、监管及产品事实。
- 对接设计/开发时，目标用户、模块职责、获批文案和 CTA 行为不丢失。
- 新资料加入时可以增量更新，而不是重建整个规则体系。

## 一次性最小交付
用户只需先交付：**现有 SOP + 一个完整真实工单**（任一存在即可开始）。其他资料持续补充，不阻塞第一轮。
