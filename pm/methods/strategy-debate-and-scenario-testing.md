# PM 页面策略：多方案竞争、逆向测试与可执行结构 v1.0

状态：METHOD_CANDIDATE。不要仅完成“有几个模块、各写什么”这一层。解决同一问题的方法可能完全不同：增强解释、改变入口、缩短表单、渠道重定向、减少错误期望、保留页面但不新建等。

## 策略无法突破时主动寻找外部异质结构
若多个方案仍是相同屏幕换标题，或 EBC 内部没有对应页面，调用共享 Reference Discovery（`assets/reference-intelligence-v0-1`）。研究直接 CFD 同类型 → 大金融相关任务 → 科技头部页面的用户任务、证据/内容顺序与行为路径；浏览器截图（PC/MB）和 HTML/互动证据分开记录。**无适用历史骨架**时可提出实质不同的结构策略；**已有用户确认的骨架**时竞争信息职责、内容深度、CTA、Variant 或轻改与不改方案，不为了“不同结构”机械加屏；用 U 用户路径质疑，不能照搬别人页面。

## 0. 当前工作必须先使用结构证据与模块准入

- 先读 [Page Structure System](../../research/page-structures/README.md) 的匹配类型和 [GPT 源码复审](../../research/page-structures/review-2026-11-13.md)；目前**全部结构仅候选，没有任何用户锁定**。
- 先从 **用户问题 → 已有模块/Variant → 必要内容 → 是否仍有缺口** 规划，而非从竞品采集的内容列表自动扩张页面。
- [Page Logic & Content Scope](page-logic-and-content-scope.md) 的 MODULE_ADMISSION_GATE 与 [Tradeoffs & Correction](decision-tradeoffs-and-correction.md) 的 HARD/SOFT 约束同等重要：建议的每个新模块要回答“为何现有模块不能承担”；方案要列明放弃的好处、取舍代价和推翻条件。
- 如果当前结构被用户明确锁定，提交新模块/删模块前需结构例外并获得用户确认；如仅为候选，依据本次真实业务可提出改动，附简短证据和取舍，不允许假称已批准。
- 必要事实、风险、活动资格和产品性质高于表面“短”和任何任意模块配额。

## 1. 方案必须解决“同一个目标”，但采用不同的路径
标准或深度任务优先比较**实质不同的解决策略**；如果只有一个明显有意义的路径，列出最强反例/不做方案并解释为什么不用凑数：
- A：低成本策略——保留已有页，调整广告承接/首屏信息/CTA/信息结构。
- B：有明确用户需求时，可改变证据顺序、CTA 策略、受众分层与模块内 Variant；**只有既有骨架解决不了时才比较结构性重构/新增模块**。
- C：可选不做/替代渠道——若根因是流量质量或 CRM 跟进，提出不新增页面的方案。

不允许把“方案 A 4 屏、B 5 屏，但文案和逻辑相同”伪装成多方案。

## 2. 给每个模块填写信息合同
| Module ID | Target segment | Prior belief | User question | Single message | Proof | Required interaction | Failure mode | Why this position |
|---|---|---|---|---|---|---|---|---|

审核：
- 这个模块的独立功能是什么？如果去掉，会丢失哪条必要信息？
- 它放在前一屏或后一屏会怎样？
- 同一信息是否出现过三次，却没有增加新证据？
- 这段内容促进“理解/正确比较/信任/行动”中哪件事？
- 是否只是在服务品牌自夸、视觉填空或设计喜好？

模块不一定与屏数一一对应。用户读的是信息逻辑，不是产品经理的 PPT 屏数。

## 3. 跨场景走读与反对意见
至少走三类用户路径（参见 user-psychology-and-journey-simulation.md）：
- 初次进入的低认知访客：会不会无法理解术语就被催注册？
- 已有认知的高意向访客：会不会需要滚动很久才找到产品规格与 CTA？
- 怀疑/期望不符的访客：会不会看到一个模糊营销承诺，随后因真实产品性质或跳转信息而退出？

对每条路径指出：
入口信息 → 第一判断 → 未满足的问题 → 可能退出点 → 页面修复策略 → 如何实测。

## 4. 方案对抗循环
S1 根据 D/R/U/C 产出完整方案 A/B，明确方案不同在哪里。
S2 以 PM 质疑者角色问：为什么这些模块按这个顺序？是用户需要还是模板惯性？
S3 以用户路径与营销承接角色反驳：广告信息是否匹配、哪些人其实不该被引导注册？
S4 以业务分析角色提出替代解释：转化不佳是否因流量/归因/后端而非页面？
S5 修订或合并方案，**明确最后选了什么、放弃/延后了什么好处、为什么接受此代价、哪些新证据会推翻**；Copy/User 若受影响需同步更新。
S6 将选择理由转成可验证假设与 Demo 验收，而不是“我认为设计漂亮所以胜出”。

若核心缺陷仍存在，继续循环；若缺真实流量证据，提交含明确待验证项的方案而非推迟全部工作。

## 6. 真正的 handoff，不是将工作全甩给设计
产物：
- 推荐方向及为什么没有选另一个；明确 `SACRIFICE / DEFERRED` 和 `FAILURE CONDITION`，**不能声称全维度都完美**；
- 页面策略叙事：用户从广告/搜索看到哪里开始改变理解；
- 每模块的信息职责、文案 ID、证据、动态与交互、CTA 及异常；
- Mobile 与 Desktop 信息优先级，不用视觉细节掩盖逻辑；
- 哪些是可以做 Demo 的模拟数据，哪些需要上线前核验；
- 回滚/变体/指标计划；告知 Design Agent **哪些内容不允许擅自改写**。

设计可以提出“这个结构表现不顺”的反馈并路由回 S/C/U，但不能自行替代 PM 改动业务推理。
