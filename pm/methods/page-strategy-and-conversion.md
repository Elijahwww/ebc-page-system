# EBC 页面策略与转化旅程：信息任务优先 v1.0

状态：METHOD_CANDIDATE；此文件是核心策略的基础参考。多方案竞争、反向推演和审查循环的执行细节见 strategy-debate-and-scenario-testing.md；用户心理见 user-psychology-and-journey-simulation.md，文案见 copywriting-critique-loop.md。

## 一、先选用户的实际任务
- 品牌/关于我们：验证 EBC 是谁、为什么值得信任、如何去正确的下一步。
- 产品页：正确理解产品机制、适用性、真实条件、信息与操作入口。
- 搜索/社媒广告 LP：解释广告吸引点与真实产品的关系，协助适配人群作出知情行动。
- 活动页：明确资格、时间、流程、规则、奖励条件和真实参与状态。

不要把所有页面优化为“马上注册”，也不要以固定屏数、统一 Hero 字数、随意数字卡强制替代内容逻辑。

## 二、每一个模块的“任务合同”

先按 [Page Structure System](../../research/page-structures/README.md) 识别用户任务可复用的**候选**结构，再用 [内容取舍](page-logic-and-content-scope.md) 和 [决策纠错](decision-tradeoffs-and-correction.md) 检查是否真需要每一个模块。历史重复出现不是效果实证，**不能靠“有三个正文槽位”就填满三个**。
每个模块写清：
- 上一个触点之后用户已经相信/知道什么？
- 此处还缺哪一个必要信息，为什么现在说？
- 提供什么主张，依据来自哪里？
- 没有这个模块会失去什么信息？如果放到别处会怎样？
- 用户的下一步是什么，若犹豫该有怎样的退路？
- 是否和其他模块、标题/副标题重复？
可以用模块表，但不能把填表本身当作分析完成。

## 三、旅程不止“进入 → Hero → CTA”
先模拟入口期望，再检查第一认知、滚动、可信证据、理解障碍、行动决定、跳转/表单、失败/返回与后续业务流程。
至少对适配用户、犹豫用户和错误期望用户走一遍。与实际观测/反馈冲突时优先修正模拟而非否认真实数据。
用户路径模拟不代表真实用户研究，也不能凭想象预测 CTR/CVR。

## 四、转化与商业结果区分
- 访问质量：受众与关键词/广告意图是否相符；
- 页面：理解、互动、错误、速度、点击、表单；
- CRM：来源是否保留、注册/Lead 是否正确记录；
- 后端：KYC、MT、FTD、客户跟进是否能完成；
- 复盘：同比/对照是否具备市场/渠道/时间/样本可比性。
对于低转化问题，应先做漏斗分层和竞争解释，而不是默认“文案/设计差”。

## 五、文案与内容归属
PM 与 Content 联合完成信息职责、逻辑与草案审查。完整文案必须经过多个角度批评、实质性重写以及对上下游用户路径的回测。
所谓“定稿”是本项目经过用户确认的内容版本，不等于历史代码是正式文案来源；代码/线上仅能证明历史实际展示版本。
设计和开发不得悄悄改变已确认文案的事实、语义和行动方向。

## 六、策略候选与对抗（每个新页面必需）
根据任务复杂度比较有实质取舍的策略，另考虑不做页面、渠道重定向或轻改。已经确认的骨架不为了凑两种结构而加屏；仅有候选骨架时允许有据增减，并说明最强反例。
- 方案 A：最小改动解决真正障碍；
- 方案 B：调整说服/证据策略、用户分层与同模块 Variant；如旧结构无法承担新的关键职责，才提出结构性调整；
- 选优：根据用户任务、证据、实现成本和失败路径，**具体写出放弃的另一项好处及何时纠错**；不是美感偏好或无代价的“全都考虑”。
选定后用用户路径重新跑一遍，若发现新的误解/摩擦，则返回 U/C/R/D 修订。

## 七、面向 Design/Development 的交接
交付时必须明确每个模块的：
模块 ID、目标用户、用户问题、唯一信息职责、对应文案 ID、证据与条件、交互状态、CTA 去向、异常、移动/桌面顺序、埋点需求、不得随意修改内容。
性能、技术组件与 UI 规范后续由设计/开发处理，PM 不需要在此阶段规定每个间距与 CSS 变量。

## 八、真实世界验证与限制
模型审查可减少内在逻辑错误，不能替代用户访谈、真实点击与 A/B 测试。
上线前遵守基本真实与风险披露：正确产品名称和状态，正确所属实体/监管称谓、真实费用和来源，不编造结果。具体地区法务审批由真正的生产项目流程决定，不用它占据第一期策略讨论。
