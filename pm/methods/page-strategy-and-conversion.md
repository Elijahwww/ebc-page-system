# 官网与推广页策略及转化路径 · v0.1

> 状态：RULE_CANDIDATE | 不把固定屏数/固定视觉风格视为通用标准。

## 先选页面任务，而不是套模板
| 页面类别 | 用户所处阶段 | 优先考虑的信息 | 转化设计 |
|---|---|---|---|
| 品牌/关于我们 | 正在验证可信度或了解公司 | 身份、业务范围、可核实证明、合作与联系 | 导航至产品/咨询/开户（以实际目标为准） |
| 产品/功能官网 | 了解适用性与交易条件 | 产品是什么、怎样运作、可用性、规格、风险、下一步 | 产品相关 CTA + 易查的说明/规格 |
| SEM / 社媒 LP | 由具体广告创意与意图进入 | 价值匹配、少量重要解释、可信证据、行动摩擦 | 单一主目标可优先，但非强制仅一个按钮 |
| 活动页 | 对参与或资格有明确兴趣 | 规则、资格、时间、步骤、风险、奖励条件 | 合格参与或咨询、清晰状态反馈 |

## 用户路径（每次项目重新绘制）
1. 入口：查询词/创意/投放受众 → 用户的预期。
2. Hero：是否第一眼理解产品/价值？需要解释什么以免误导？
3. 证明：何种信息足以消除该用户的关键顾虑？是否是已批准可用事实？
4. 摩擦：页面长度、表单字段、跳转域名、语言、地域及风险告知是否阻碍用户？
5. 行动：CTA 导向、目的地是否可靠、错误/不可用状态如何处理？
6. 后续：成功/失败/放弃如何记录，是否返回 CRM 或业务追踪系统？

## 结构提案输出
每个模块必须写明：`id` / `user_question` / `single_message_job` / `source_evidence` / `proposed_copy` / `visual_role` / `interaction` / `CTA` / `tracking` / `risk_or_dependency`。
没有具体用户问题或商业目的的模块，应优先质疑而非默认添加。

## 文案/设计/开发边界
- PM 负责确定模块职责、用户路径、事实/产品前提、CTA 目标与验收条件。
- 正式文案以批准的 Page Content Source 为准。设计或开发不得代写、修改或翻译获批文案。
- 设计 Agent 可提出可读性或信息密度问题，但要返回 Content / PM 审核，而不是擅自修改。
- 代码必须实现真实 CTA 与表单目的地；未获得接口时做明确 Demo 占位，不伪装真实提交。
- 多语言本地化按市场语义与术语表，不进行未经批准的金融承诺增删。

## 埋点建议（按有权限的数据环境实施）
`page_view`（页面版本/国家/语言/渠道）→ `primary_cta_click` → `form_start` → `form_submit_success` / `form_error` → 可归因的 `qualified_lead`。
埋点定义必须写明去重、事件时序、Consent/Privacy、跨域及 UTM 继承、历史漏斗可比性。未真正部署前只能标记 `TRACKING_PROPOSED`，不得宣称真实转化有效。

## 评估
没有真实对照实验时，以用户理解、事实准确、响应式可用、表单正确性和实施质量做先验评审；有足够且适当的对照数据时再评估转化效果。避免把漂亮截图直接等同业务成功。
