# EBC 方案取舍、放弃成本与纠错协议 · Decision Tradeoffs & Correction v0.1

> 状态：METHOD_CANDIDATE / UNLOCKED_STRUCTURE_NOT_APPROVED / 2026-11-13
> 触发：用户反对 AI 产出“什么都照顾、什么都很好”的伪完美方案。此文**补充**现有 D/R/U/C/S、S 节点对抗及 `page-logic-and-content-scope.md`，不复制另一套 PM 流程。Claude 的 10 份 `research/page-structures/` 报告已在 main；本次按真实源码/locale 和结构报告进行复审，尚未经过线上验收，本文件不对具体结构作最终裁决。
>
> 原则：**方案不必在每个维度都更好；它必须在当前目标、事实、业务约束与成本下，做出可解释的选择。** “多方案”是为了找出真实冲突与放弃项，而不是让每个方案都被描述成完美。

## 1. 五类「必须明确冲突」的取舍维度
对当前项目只选择真正相关的 2–4 项，不让 Agent 为填满框架虚构约束。

| 不可全要的目标 | 常见真实冲突 | 优先判断 |
|---|---|---|
| **用户理解 vs 页面简短** | 新手需解释 CFD/参与规则，高意向用户想快进 | 保留关键事实/资格/风险；将次级细节融合、展开或下沉，**不删除必要信息** |
| **获客转化 vs 预期准确** | 激进 CTA 或优惠宣传可能推高点击，却误导不适用用户 | 禁止以点击增加抵消错误合规/产品承诺；正确理解是硬底线 |
| **品牌展示 vs 当下用户任务** | “EBC 全球优势”看似完整，但比赛页本来要让人判断奖品/规则 | 不是所有品牌事实都应出现；先选择对本次决策提供证据的部分 |
| **结构一致 vs 业务差异** | 交易激励的抽奖/达标/排名可能共用页面骨架，但机制与数据不同 | 优先相同 Module + Variant；真实新机制无法容纳才提交 Structure Override |
| **视觉吸引 vs 操作效率/性能** | 3D、复杂动效提升印象，也增加负担与开发维护 | 特效必须有视觉职责，不能阻断操作和必要信息；对性能/可访问性做真实复核 |
| **速度/成本 vs 完整实现** | Demo 前端可以交付，但正式接口/CRM 依赖未齐 | 明确阶段性产物、Mock 与真实后端边界，禁止用假完成掩盖成本 |

## 2. 先硬约束，后权衡（不搞“各方面 9/10”伪精确评分）
**HARD / 不可权衡**：用户最新明确要求；真实产品性质/状态；获批 copy 与合法使用限制；相关地区必须可见的风险/活动规则；技术上必须可用的核心流程；数据与素材真实性。违反硬约束的方案先排除，不能用高颜值、高点击或节约时间来抵消。

**SOFT / 可权衡**：正文深浅、模块信息多少、视觉记忆点、页面篇幅、实现成本、未来维护、多语种复杂度、非关键动效。权重来自本次任务的目标和可观察证据，不是全局常量。

当两个软目标不可兼得，**明确指出我们选择优先保护哪一个，放弃或延迟哪一个**；不能说“全都兼顾”却没有实质取舍。

## 3. 推荐方案必须通过四重选择测试
1. **真实分歧**：A、B 方案在可交付结果/成本/用户路径/目标上到底有什么冲突？如果只是同一骨架换标题，取消伪比较，改比较该结构下的内容层级、模块 Variant、互动或最小实现。
2. **被支配方案淘汰**：若 A 在同等硬约束下，既没有比 B 更好解决目标，也不更便宜/更快/更可维护，只因“内容更全面”而多出三屏，优先舍弃 A。不要为凑两方案保留无意义选项。
3. **反事实减法**：拿掉一个模块、一种功能、一段证明或一个复杂动效，用户哪项关键判断会受损？如果损失不具体，优先移除/合并/下沉；必要事实用就近短说明不等于必须加独立屏。
4. **逆向失败**：假设最终上线后方案失败，最可能不是因为“设计不够炫”，而是哪一个前提不成立？写出**可观察的失败信号**与回退方式；缺数据则明确是低信心假设而非假定成功。

## 4. Decision Record：要写出选择后的牺牲，而不是全优卖点表
每个真正的重要分歧只用一张紧凑的「取舍记录」，不要生成一份庞大打分报告：

| 字段 | 要求 |
|---|---|
| DECISION | 当前到底要选择什么？只选一个实际可行动的方向 |
| PRIORITY / HARD CONSTRAINT | 当前最重要的目标和不可违反的约束是什么？ |
| CHOSEN / REJECTED | 哪一个被选中，主要竞争方案为什么落选？如果已有 `STRUCTURE_LOCKED`，候选可以是同结构内不同信息深度/Variant，而非新增模块 |
| **SACRIFICE / DEFERRED** | 为了选中 A，**明确放弃/延后**什么好处？用户可能承担哪种代价？ |
| FAILURE CONDITION / REVERSAL | 什么新证据会让决定不成立？例如用户找不到关键规则、活动机制新条件不能在原模块表达、移动端关键行动被隐藏。出现时返回哪一节点、由谁复审？ |
| CONFIDENCE / EVIDENCE | 属于用户明确确认、代码/页面观察、真实用户行为数据、竞品信号、模型推断中的哪类？没有实际数据不得声称最优 |

**简洁推荐句式**：
> 建议采用 A，因为它最优先解决 X。为此我们主动不做 Y，代价是 Z；暂时接受该代价，因为有证据/假设 W。如果出现可观察信号 K，就回到 S/U/R 改为 B 或提出 Structure Override。

不要求每个 CTA 文案微调都完整填表；STANDARD/DEEP 的高影响方案和新增模块争议才强制写一次。

## 5. 三种纠错触发（CORRECTION GATES）

### C1 · 事实纠错
发现新的官方产品资料、活动机制、真实资格/费用、代码/线上矛盾、用户最新确认，**撤销旧结论**；更新 Copy/Structure/PM 决策来源。不是“新版本更高级就覆盖旧确认”。

### C2 · 策略纠错
用户路径无法完成、入口人群假设不成立、某模块没有新增信息、成本超出阶段目标或多轮自审只改同义词 → 回到 D/R/U/C/S 中最相关节点；先诊断真正限制，再决定删减、调序、同模块变体还是新增。

### C3 · 结果纠错
真实用户评审、浏览器操作、营销/转化数据或技术接入揭示问题 → 按证据更新方案；不得用模拟人设、假的 CTR/CVR 或模型自评替代真实观测。用户明确拒绝视觉或页面结构时应标未通过，不以功能测试 PASS 推翻用户反馈。

### 停止条件（避免无限纠错）
- 当前硬约束满足、关键用户路径可执行；主要结构及信息选择有证据/明确假设支撑；
- 被拒方案、牺牲与可反转条件已记录，且本轮没有实质新证据支持再修改；
- 剩余争议属于可测试、可回退或确实需用户判断的价值分歧；
- 标 `DECISION_READY_WITH_ASSUMPTIONS`，**不表示“最佳”或用户已批准**。当出现 C1/C2/C3 的新信号再回到相应节点，而非自我循环到所谓完美。

## 6. EBC 的具体示例（说明方法，不是裁决结构）

### A. 三种交易激励活动（已核对上传的 Vue/locale，在线未核验）
- 候选共享：Hero 内嵌注册、奖品、参与步骤、规则；条件位可能随抽奖/达标/排名变化。
- 权衡：统一的结构有助于理解和维护，但某种新的真实赛制/领奖限制也许需要更多解释。选**结构复用 + 机制 Variant**，放弃「每个主题都全新 8 屏营销叙事」的视觉噱头；如果新机制的关键资格不能清晰落在奖品/机制/规则，提出 Override，不强制藏起来。
- `LIVE_NOT_VERIFIED` / `STRUCTURE_CANDIDATE`；不称所有线上活动都已验证。

### B. 产品推广页“7/7 都是三个正文模块”
- 这是**历史案例一致性**，不是转化或认知的最优证据；样本可能来自同一共享代码或组织模板，并不独立。
- 权衡：三个槽位可成为默认复用方案、节省创作和维护；代价是复杂新产品可能信息解释不足。**不将 `3 sections` 写成 HARD RULE**。当必要风险/产品机制无法清晰由现有模块处理时允许内容布局/结构例外，并标明证据。
- ETF 2026-09-12 活动到期是内容真伪问题，**不能为了填满第三槽位而自动新增 “为什么选择 EBC”**；先核实当前活动/业务、用户路径，再决定现有内容角色。

### C. EBC Share v1→v2 视觉
- v1 用户认为过密、传统；v2 Claude 报告改善布局/动画但仍待审美认可。
- 不能说“所有功能 + 更多交互 + 强科技 + 最少密度 + 零成本”全部同时保证。
- 要在首屏高频工作入口与公告/社区/积分间选择视觉主次；非主角信息可摘要，完整功能仍在二级页面。可牺牲“首页所有信息一眼可见”，换来清楚的工作动线；当真实用户因藏得太深找不到操作，重新提升相应入口。

## 最终原则
