# EBC 页面逻辑与内容取舍 · Page Logic & Content Scope v0.1（讨论草案）

> **状态：METHOD_CANDIDATE / UNLOCKED_STRUCTURE_NOT_APPROVED / 2026-11-13。** 用户明确要求减少 AI 自动新增无效模块、冗长页面与跨模块重复，同时不牺牲必要信息、合规事实、用户理解与设计创新。
>
> 这是现有 `pm/operating-system/iterative-pm-engine.md` 和 `pm/methods/page-strategy-and-conversion.md` 的**执行层补充候选**，不是另一套完整 PM 系统。等 Claude 的 `research/page-structures/` 历史类型分析入库后，联合校对，才决定升级为 AGENT 强制规则。
>
> **一句话**：先说明页面要让哪个用户完成什么判断，再决定该提供什么信息；**结构优先复用、内容从用户认知缺口来、增加模块须举证、缺失关键事实不可用“简洁”掩盖**。

## 1. 为什么之前的 D/R/U/C/S 仍可能产出过长页面？

现有 PM 系统已经要求：同一模块的独立职责、研究真实性、Copy H1/subtitle 不重复、对 S 结构反证。这一基础**不能推倒重来**。本次缺口主要是以下四项：

1. **Research-to-Page 失控**：调研发现 15 个不错的竞品卖点，Agent 就想为其中每个创作一个新区块。调研发现不等于目标用户当前必须看到。
2. **Question-to-Module 失控**：模拟的 7 个用户疑问被误解释为 7 个独立模块；即使其中 4 个可以被已有步骤/规则/机制顺带回答。
3. **Strategy-to-Structure 失控**：原 PM 方法默认鼓励两种“结构不同”方案；当页面已存在**用户批准的结构合同**时，不应为了满足方案竞争硬造新模块。
4. **Copy-to-Length 失控**：一个卖点在 Hero、优势卡、品牌说明和最后 CTA 被四次重复；微观句子写得好，不等于宏观叙事有效。

**更深分析 ≠ 更多页面内容**，**更全面地研究 ≠ 所有分析必须出现在页面中**。将 PM 决策日志留在 `pm-decision.md` 或 `runs/`，不要自动写进 UI。

## 2. 首先锁的是「用户判断任务」，而不是屏数

在写页面骨架前，仅用本项目确有证据的内容确认：

| 变量 | 必答问题 | 缺证据怎么办 |
|---|---|---|
| 主要任务（ONE JOB） | 用户读完必须能理解/决定/操作的第一件事是什么？ | 从原始需求提取，标假设 |
| 入口与意图 | 从 Google 搜索、广告、CRM、站内导航、社区转发哪种入口来？ | 不虚构渠道；按可识别来源建 1–2 情境 |
| 认知起点 | 用户进入前已有知识是什么？什么仍不清楚？ | 竞品/搜索意图仅是线索；无用户研究标 HYPOTHESIS |
| 信任与阻碍 | 影响这一次决策的最大误解、资格/成本/交易限制是什么？ | 优先来源可验证的真实机制和反馈 |
| 成功行动 | 用户在哪里完成报名、查看规格、申请、阅读或注册？ | 无真实去向时 Demo 清楚标明 |
| 必需信息边界 | 哪些条件/风险/奖品资格/收费/市场实体必须可见？ | 不能为了短页面而删；有缺口标 BLOCKER |

**核心是用户理解的变化**：`进入时已经知道 A → 必须补齐 B → 读完能合理决定 C → 明确下一步 D`。

不强制“营销页面只能 3 屏”“一页最多 5 模块”“所有页面都必须 One CTA”之类无证据配额。页面长短由用户任务、信息复杂度、事实与法规要求决定。

## 3. 结构优先级：已确认骨架 → 同模块变体 → 局部信息 → 独立新增模块

**入口补充**：先按 [Page Type × Mechanic × Hero Conversion 三维匹配](../../research/page-structures/matching-and-hero-contract.md) 识别 EBC 活动页/产品 LP/官网。**Hero 右侧内嵌表单是历史 Campaign 的默认候选，不是固定业务定义**；用户明确要求 CTA 按钮时，按真实去向替换 Hero 入口，通常无需独立增加注册模块或重新设计整个活动结构。结构不匹配则按 EBC 官方页面 → CFD → 数字币 → 更广金融行业的研究梯度补证据。

按照证据/权限选择：

1. **STRUCTURE_LOCKED（用户明确确认、且适用本市场/任务的版本）**：默认保持模块与顺序。新主题首先替换对应视觉、文案、奖品、真实数据、交互与 `Variant`。禁止模型为了“内容更丰满”“更有高级感”擅自新增一屏。
2. **CROSS_CASE_CONFIRMED 但尚未由用户批准**：作为强候选基线，按真实任务测试；出现适配障碍可以提出方案和理由，不能擅自标成已锁定。
3. **SINGLE_CASE_CANDIDATE / NO_PATTERN**：从 D/R/U 推导最小充分结构，并用竞争方案验证；不能把一页历史源码误当公司统一法则。
4. **强制业务事实/法规**：若已批准骨架无法容纳当前必需披露/资格/交易条件，必须触发 `STRUCTURE_OVERRIDE_REQUIRED` 或合规/事实冲突记录；不得悄悄省略，也不能把“没有批准新增屏”当作隐藏风险的借口。

针对既有 `S` 节点“至少两种结构方案”的要求：**有已锁定结构时，竞争的是内容组织/主次/证据/CTA/同模块 Variant，而不是强迫产出另一个模块数量不同的结构；真有无法用原结构解决的新需求，才提出独立的结构 Override**。本次集成已同步修改 PM Skill 和核心策略方法，后续用真实回归验证 Agent 是否遵循。

> Claude 已提交 Campaign/LP/Website 结构候选到 main，但不能将其历史观察自动视为已锁定结构，本文件不预设任何实际类型已获锁定。用户举例的 `Hero → 奖品 → 排行榜/机制 → 步骤 → 规则` 已由三个原始活动源码支持为**历史候选骨架（机制条件位 2/3）**，尚未与线上核验。

## 4. 新增模块准入门槛（MODULE_ADMISSION_GATE）

给每个拟新增的营销/解释模块做**五问**，不要为了填报告而填报告：

1. **真实缺口**：它解决的是当前目标用户在这个节点尚未得到答案的重要问题吗？从原始需求、真实行为、研究还是模型猜测得出？
2. **不可被现有模块吸收**：为什么已有 Hero / 机制 / 奖品 / 步骤 / 规则 / FAQ / 产品规格等模块或内部变体无法有效承接？
3. **不可被现有内容证明**：它新增可验证的事实、具体差异、决策条件或行动能力吗？还是重述“专业、可信、国际、强大、创新”？
4. **位置与行动价值**：为什么必须在这个位置让用户看见？如果删除或移动，哪条真实决策路径会断？能否用行内说明、模块内卡片、详情入口、按需展开代替？
5. **代价与约束**：加一屏会增加多少认知负担/用户等待/开发与多语言维护？是否与已锁定模块、合规或内容版本冲突？

若问题没有坚实的回答，**默认不新增模块**；按下表处理。若用户明确要求新模块且不违法、不破坏事实，按最新明确要求执行，并保留变更记录。

## 5. 内容落点的五种处理：不是只“保留/删除”

| 决策 | 条件 | 实施方式 |
|---|---|---|
| **KEEP_VISIBLE** | 核心用户判断必须立即知晓；对参与资格、关键成本、重大风险或产品性质等不可延后信息 | 放在决策前能看到的合适位置；保持正确层级与易读 |
| **MERGE_INTO_EXISTING** | 内容真实但与现有模块同职责 | 合并为同一段、卡片字段、步骤注释或同一模块 Variant，避免整屏重复 |
| **DISCLOSE_ON_DEMAND** | 仅特定用户/后续阶段需要的细节，且不影响当下知情决定 | 可达的 FAQ、规则展开、详情弹层或下一级页面；入口明确，不能藏必需披露 |
| **LINK_TO_SOURCE** | 更长的规则全文、完整规格、历史资料或附属教育内容 | 从对应模块给清晰去向，明确“这里是什么”，并保留当前必要摘要 |
| **OMIT_FOR_THIS_TASK** | 无关、无有效证据、同义重复、其他页面已有且不影响当前任务，或已过期内容 | 不进入当前页面；研究资料仍可留在 PM 记录/来源索引 |

**可见信息并非全部要变成“屏”**。一屏也可以有层级清楚的必要内容；反之一个极短的空洞 Hero 也可能让用户不知如何继续。

## 5A. 方案取舍与纠错（不制造“全都正确”的假完美方案）

请联合阅读 [方案取舍、放弃成本与纠错协议](decision-tradeoffs-and-correction.md)。本协议额外要求，在当前项目确有竞争性取舍时记录：
- `CHOSEN`：选了什么以及当前核心目标/硬约束；
- `SACRIFICE / DEFERRED`：**主动放弃/延后了哪些看似不错的功能、模块、视觉主张或用户便利**；
- `REJECTED`：最强的备选方案为何落选，而不是把所有方案描述成同样优秀；
- `FAILURE CONDITION`：哪一条新证据会推翻推荐、需要回到哪个 PM 节点；
- `EVIDENCE LEVEL`：实际已观察/获用户确认还是推断。

已锁定的页面骨架内，同样可以对内容深度、模块 Variant、CTA 与视觉主次做真实取舍。不要为了凑多方案而新造一屏；也不要把“所有维度都完美”当成成功标准。

## 6. 页面逻辑的「减法审查 + 完整性审查」成对执行

### PASS A：内容取舍（REDUNDANCY REVIEW）
- **跨模块重复**：能否用一句话描述每个模块的独有新增信息？若描述一样，先考虑合并或重写职责。
- **首尾重复**：底部 CTA 可以再次出现以方便行动，但不应该复制另一段一模一样的卖点叙述。
- **卖点堆积**：品牌、平台、合作方、监管、活动奖励不能因为“EBC 有”就全部放到每个页面。只保留对本次决策提供证据的事实，以及必须披露的内容。
- **自我生成理由**：不能因为某个模块已经在代码里被 AI 生成，就反向论证它有必要。
- **研究滥用**：竞品某模块流行 ≠ 本项目用户需要；竞品顺序/视觉只是候选观察。

### PASS B：必要完整性（SUFFICIENCY REVIEW）
- **误导/信息气味不足**：用户进入后是否知道自己来对地方、产品/活动到底是什么？绝不能为“清爽”只剩抽象大图和空洞标题。
- **参与条件**：真实资格、时间状态、奖品领取条件、排名口径、关键费用、必要风险能在做决定前获得吗？
- **不同意图**：高意向用户有直接路径；第一次接触用户有适度解释；误点/不符合资格用户不会被误导。
- **失败恢复**：操作失败、需登录、地区不适用或活动结束时有真实而清楚的状态。
- **可验证**：所有数字、费用、监管身份与案例事实标明依据或 Pending；不因填视觉空间杜撰数据。

如两项审查冲突，应在当前模块**改变呈现形式**，而不是一律增加或删除一屏。

## 7. 页面深度分层，不是强制短页面

| 任务与信息复杂度 | 默认内容深度倾向 | 不适用的机械做法 |
|---|---|---|
| 已认知主题、目标单一的 Campaign/广告入口 | 主题、奖励/资格、参与机制/行动为主；条件规则易找到 | 为每个“营销优势”单独生一屏 |
| 新手面对不熟悉的 CFD/Pre-IPO 产品 | 需要足够机制解释、资格、成本与风险，关键 FAQ/规格可达 | 强制做成 3 屏导致误解产品性质 |
| 官网品牌/公司介绍 | 足够可信、可核查的故事与证据，允许适当长叙事但每段信息新鲜 | 既不能单屏口号，也不能品牌奖项全部独立铺 10 屏 |
| SEO 产品信息页 | 搜索意图、产品事实、真实规格和问答可能要求更长篇幅 | 把“短”当唯一好指标或隐藏 SEO 实质回答 |
| 工作台/高频功能页 | 初始任务优先、列表与详情按需展开，允许高频用户需要的密度 | 一味留白、把所有操作藏进多个层级 |

参考：GOV.UK 与 ONS 的用户需求先行、分组/内容框架；NN/g 的渐进披露和首页足够 Information Scent。外部方法只是一般设计证据，**不代表 EBC 已通过真实用户实验**。

## 8. 极简可执行的 Page Logic Contract（设计/代码前交付）

仅维护一张小表即可，不额外生产五份互相重复的文档：

**Header**：`page_type | structure_source/version/status | target_market | entry_intent | primary_user_job | target_action | verified_core_facts | content_complexity | copy_version`。

| 模块 ID / 顺序 | 用户进入前还缺什么？ | 该模块唯一补充的信息 / 证据 | 用户看完后知道/能做什么？ | 决策 | Copy ID/来源 |
|---|---|---|---|---|---|
| Hero | 当前主题/状态/下步不清 | 一条主题事实 + 主行动 | 确认来对地方、知道下一步 | KEEP_VISIBLE | 待项目 |
| 奖品 | 不知道参与价值/资格 | 奖励内容+重要领取条件 | 判断是否值得了解规则 | KEEP_VISIBLE | 待项目 |
| 交易机制/排行榜 | 不知道如何比较或衡量 | 本次机制/排名口径及状态 | 知道怎样参加/如何计算 | 按真实骨架 | 待项目 |
| … | … | … | … | … | … |

**Exception log**：`requested_new_module | unmet_user_need | evidence | why_existing_modules_fail | intended_location | risk/cost | status(APPROVED/PENDING/REJECTED)`。

**用户最终看到**：优先只展示推荐骨架、需要修改/删减的内容及最关键理由；研究证据与争议保留内部记录。不要将 PM 深度自审记录直接渲染成页面内容。

## 10. 需要回归验证的五个场景（NOT_RUN）
- **PL-01 / 活动已锁结构**：新交易赛主题触发旧骨架下内容替换，不凭营销灵感新增“为什么选择 EBC / 教育 / 精彩瞬间”模块。
- **PL-02 / 结构确有缺口**：真实新比赛形式多了一项重要资格/战队结算规则；先尝试机制/规则承接，确实不能承接时提出结构 Override，不默默藏掉条件。
- **PL-03 / 新用户 SEO 产品页**：需要真实机制、交易条件与风险，不能因为“减法”将必需信息剪掉。
- **PL-04 / 官网品牌页**：监管与可信证据已在一段明确传达，不为填满页面再加三段同义“全球专业”。
- **PL-05 / 高意向 LP**：来自明确广告的用户应快速知道所广告主题、条件和行动路径；不复制无关的宏观教育和集团历史模块。
